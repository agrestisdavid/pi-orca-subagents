# POS — Pi Orca Subagents

POS contains the full pi-subagents engine. Use its native profiles, budgets,
permissions, context handling and workflow controls. No separate pi-subagents
or Todo installation is required. Todo is loaded from POS's own dependencies.

## Start a bounded task promptly

When the task already specifies the workspace, agent profile and model, use
those values and dispatch. The native launch checks resolve the installed
profile, model and Orca connection. Do not investigate configuration files,
model registries, previous runs or implementation source to re-prove those
inputs before starting. Do not perform the child's assigned inspection in
the parent first.

If a required input or tool parameter is missing, resolve only that item:
use the tool's schema or one targeted capabilities/guide lookup. Stop once it
is resolved. Read a workflow reference only when the workflow needs it.
Follow explicit user requests for investigation or planning before execution.
On a real launch error, preserve the original error and receipt; follow the
recovery rules below rather than silently trying another model or execution mode.

`model` accepts a configured short id with a thinking suffix, for example
`model: "model:low"`. Pass that string unchanged when it is requested. Do not
add a separate `thinking` dispatch field or convert it to a provider URL.
Omit the model override when the task should use the profile's configured model.
Native scripts pass per-child parameters to `await runs.run("step", {...})`;
structured values are in `result.structuredOutput`, and `runs.ref(result)`
provides the run reference. Use `result.ok` to gate dependent steps.

## Launch

For POS requests, default to interactive Orca children:

```typescript
pi_bots({
  action: "start",
  execution: "orca-tui",
  coordination: "orca",
  viewMode: "orca",
  dispatchView: "shared",
  launch: { agent: "scout", context: "fresh", task: "The bounded task" }
})
```

For implementation use an appropriate writer profile instead of scout. Parallel
and dynamic work uses native `workflowScript` in `launch`. Keep work asynchronous
unless the requested contract requires foreground execution. Native completion
notifications wake the parent; do not poll or call `bg_wait` just because a
notifying native child is running.

If the user explicitly requests headless/native work, use native `subagent`,
or `pi_bots` with `execution:"headless", coordination:"native", viewMode:"none"`.
Missing Orca is a start error, not permission to silently change execution mode.

Every TUI child creates and updates its own Todo plan. At startup only `todo`
is offered; after a successful `todo` create, the originally permitted work
tools become available. The first call must create the child's plan (or clear
inherited todos before creating it), without parallel work calls. Update the
current item to `in_progress` before work. Capability ceilings still apply.
Use native supervisor request IDs and confirmed replies; an Orca-only
message does not answer a native question. Lost start/resume replies must be
recovered by receipt, never by launching a replacement child.

Each child occupies one tab: use its assigned dispatch tab; if no free assigned
tab exists, create one Pi tab. The actual parent in Orca coordinates through a
background adapter, with no additional visible coordinator tab per child.
Closing owned tabs stops their native work by default, controlled by
`/pi-bots-settings`. Keep the dispatch tab open until completion.

## Output contracts and review loops

Separate execution status from the domain judgment:

- A child that delivered its result successfully is a **successful execution**
  even when its verdict is negative (for example a review with
  "changes required"). Report it as such: *Review completed – changes
  required.* Use the native run status for execution failures, including
  unmet mandatory output requirements.
- Ask review children for the **structured result only**. `structured_output`
  ends the child's turn; every mandatory artifact must exist **before** that
  call. A requested Markdown report is generated by the parent from the
  structured result afterwards, never written by the reviewer as a second
  contract surface.
- If a contract explicitly required an additional file and it is missing,
  report exactly: *Output contract not fulfilled; structured result exists.*
  Preserve the native failure status for this unmet requirement and retain
  the structured result. Distinguish the missing file from the review verdict.
- Missing optional result fields must never abort a workflow; omit them or
  give them JSON-compatible defaults in the schema and the task text.
- Finished successful results are reused through run/receipt/artifact
  references. A configured reuse reference is never an authorization for a
  replacement run: an active (running/queued/detached), failed, unknown, or
  unresolvable reference (including status transport errors) stops the
  workflow visibly with status `reuse_blocked`, preserving the reference and
  the observed state — no replacement run, no dependent step. Only a status
  reporting `State: complete` without error markers is reusable.
- Infrastructure errors stop dependent steps; review findings lead into the
  next fix round. Exactly one writer per workspace, fresh review contexts.
- On Windows, every child (TUI and native) receives a short verified
  execution context: the actual Node path, the temp directory, and – only
  when present – the project interpreter at `.venv/Scripts/python.exe`.
  It also explains Git Bash backslash handling and that MSYS paths
  (`/tmp/...`, `/c/...`) must be converted before they reach Windows
  programs. No user-specific paths are hardcoded and no interpreter is
  installed.

For a Scout → Worker → Review → fix-round loop use the tested reference
template [templates/scout-worker-review.mjs](templates/scout-worker-review.mjs)
(config block at the top: workspace, agent profiles, tasks, up to three review
rounds). It implements the rules above and is covered by
`test/pos/workflow-template.test.mjs`.

## Acceptance criteria and reporting

When accepting a POS change, verify at minimum:

- 300 identical status updates produce a single parent notification; a child
  failure is announced once per transition (run, child, cause, outcome).
- Workflow scenarios behave as specified: direct success, one fix round,
  round limit (no fix after the last round), infrastructure error (dependent
  steps stop), reuse of finished successful results, and visible reuse blocks
  (invalid reference, status transport error, running writer, failed run) with
  no replacement run and no dependent steps. Missing optional fields never
  abort a run.
- TUI reliability: the closed-tab view reopens into the correct workspace,
  one late `ready` does not resurrect a closed view, and file exchange
  survives transient Windows rename failures.

Report acceptance results as three separate lists — **bestanden** (passed),
**fehlgeschlagen** (failed, with the observed error), **nicht geprüft** (not
verified, with the reason). Never merge unverified items into passed.
